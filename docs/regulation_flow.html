Regulation flow: intake → review → SysX2

Traced from orchestrator/orchestrator.py, dynamic_crawler/formfill/orch.py, crawler/generic_crawler_wrapper.py and apis/pipeline_api.py — every box and API label is a real class, table or endpoint in the code, except the sync step, which is marked proposed because it doesn't exist yet.

What "accept" actually does Accepting a regulation does not remove it from your database. POST /update-status/regulations just flips regulations.status to 'accepted' — the row stays exactly where it was, same as a rejected row stays with status = 'rejected'. The difference is that an accepted row should additionally be copied out to SysX2's database. Today nothing in this repo performs that copy — there's no scheduled job, no webhook, no endpoint that reads accepted rows and pushes them anywhere. I've named it POST /sync/regulation/{id} in the diagram as a placeholder for what that endpoint could be called; it isn't real yet.
What are extracted requirements actually compared against? compliance_req, demo_control, demo_kpi and their linkage tables (demo_req_control_link, demo_req_kpi_link) aren't generated from scratch by this pipeline — their baseline is meant to come from SysX2, the same external system the accepted regulations get synced to. Today that inbound side doesn't exist in this repo either: get_all_compliance_requirements() just selects whatever rows already happen to be sitting in the local table, with no import job feeding it from SysX2 first. The only thing this repo's code actually writes into those tables is its own output — every requirement/control/KPI that comes back match_status = "new" gets inserted locally (IS_SUGGESTED = 1) via insert_new_suggested_requirement() and friends. So right now the "existing catalog" a new regulation is matched against is really just whatever was manually seeded plus everything this pipeline has suggested on prior runs — not SysX2's real catalog, until that inbound sync is built.
Do updates (new versions) also reach SysX2 through accept/reject? Structurally, yes — that's the same path. When the crawler sees a document again and its content_hash differs, Classify & version archives the old content/analysis and produces a fresh version, which flows through DB1 → DB2 → Reviewer → Decision exactly like a brand-new regulation. So accept/reject on that re-analysed row is the mechanism that would (once the sync step exists) push the update to SysX2.

The gap: nothing in the code today resets regulations.status when a new version lands. If a regulation was already 'accepted' and gets modified at the source, it silently stays 'accepted' — there's no 'pending_review' state or equivalent to tell a reviewer "this one changed, look again." A reviewer would only catch it by re-opening that regulation on their own. That reset is a second proposed piece, alongside the sync step itself.

The crawlers and the Orchestrator / NewOrchestrator classes aren't HTTP APIs — they're the Python layer that /trigger/* calls into internally. The regulator source websites aren't an API either — they're the external HTTP endpoint the crawler visits.
